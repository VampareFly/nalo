# Apple 登录接入需求

## 基本信息

- 日期：2026-09-16
- 当前状态：开发中；已接入 `configs/list` 的 Apple 登录开关，待服务端允许未登录访问及联调
- 实现基准：复用现有 Flutter + Riverpod + MVVM 登录架构，不影响 Shopify 登录流程
- 调用方向：View → ViewModel → Repository → Service → Apple Authentication → Nalo 服务端

## 目标

在现有登录入口页增加 Apple 登录能力：

1. 使用 `configs/list.data.show_apple_login` 控制 Apple 登录入口，首次安装默认展示。
2. 使用 `sign_in_with_apple` 获取 `identityToken` 和 `authorizationCode`。
3. 将 Apple 返回的身份 Token 发送到 Nalo 服务端，换取统一的 App Session。
4. 复用现有 Token 存储、Session 生命周期、登录结果埋点和登录后分流能力。

Apple 私钥、Team ID 和 Client Secret 只能由服务端保存，Flutter 不保存或请求 Apple 私钥。

## 流程顺序

```text
登录入口页
  ├─ App 启动时同步准备 Apple 登录首帧值：有缓存使用缓存，无缓存默认显示
  ├─ iOS 登录页首帧直接使用该值，不先显示默认值再切换为缓存值
  ├─ iOS 后台请求 configs/list
  │    ├─ 返回 1 → 显示 Apple 并缓存 true
  │    ├─ 返回 0 → 隐藏 Apple 并缓存 false
  │    └─ 失败或字段无效 → 保持缓存或默认值
  ├─ iOS 无缓存且首次请求失败 → 仅在网络由离线变为在线时补试
  ├─ Android → 永远不显示 Apple，不为该开关发请求
  ├─ Continue with Apple
  │    ├─ Apple 原生授权
  │    ├─ 获取 identityToken 和 authorizationCode
  │    ├─ POST /api/v1/app/auth/social/login
  │    ├─ 保存 Nalo App Session
  │    └─ 进入现有登录后分流
  └─ Continue with Shopify
       └─ 保持现有 Shopify OAuth 流程
```

## 1. 登录入口页

### UI

- 在现有 Shopify 登录入口附近增加 Apple 登录按钮。
- 使用 Apple 官方通用图标和文案：`Continue with Apple`。
- 图标使用 Apple 登录规范中的 Apple 标志，不自行绘制或使用与 Apple 标志相似的图形。
- 按钮视觉风格遵循 Apple 登录按钮规范，并与现有登录页整体间距、圆角和 Loading 状态保持一致。
- Apple 登录请求进行期间，复用现有页面级 Loading，禁止重复点击。

### 显示配置

- 接口：`GET /api/v1/app/configs/list`，从统一响应的 `data.show_apple_login` 读取整数 `0/1`。
- `1` 显示，`0` 隐藏；缺失、类型错误、其他值均视为无效响应，不覆盖缓存。
- iOS 每次进入登录页先读取本地永久缓存；无缓存时默认显示 Apple，不保存时间或设置过期时间。
- App 在 `runApp` 前预加载本地缓存，并通过 Provider 注入首帧状态：缓存为 `true` 时首帧显示，缓存为 `false` 时首帧隐藏，无缓存时首帧默认显示，避免冷启动期间 Apple 按钮先出现再消失。
- 同次进入登录页后台请求服务端配置；成功后立即更新 UI 与缓存，失败时保持当前状态。
- 服务端返回值与缓存不一致时，允许后台刷新完成后更新一次 UI；该变化代表服务端最新配置，不属于首帧闪烁。
- 仅当本地尚无该配置时，在首次请求前订阅网络状态；若首次请求失败，等待 `connectivity_plus` 报告“无网络 → 有网络”，再补发 `configs/list`。补试成功后写入缓存并结束监听。
- 已有缓存时仍每次进入登录页正常请求一次最新配置，但不监听网络恢复，也不因网络变化额外请求。
- 不使用固定延迟、权限弹窗关闭或 App 生命周期恢复作为补试触发条件；网络状态只是重试时机，不等于 API 可达。若 iOS 未报告该状态变化，则本次页面不会自动补试，下一次进入登录页仍会请求。
- Android 永远不展示 Apple，也不因登录入口开关请求该接口。
- Shopify 登录入口不受配置请求影响。
- 该接口在首次安装且尚未登录时必须可访问；客户端以 `requiresAuth: false` 请求。若服务端仍强制鉴权，只能使用缓存/默认值，无法实现首次进入时远端控制。
- 已登录的检测模块也使用 `configs/list`，但其配置解析和调用保持独立。

## 2. Apple 授权

### 客户端授权

- 使用 Apple 官方 Sign in with Apple 能力获取授权结果。
- 客户端只使用 Apple 返回的 `identityToken` 作为服务端登录凭证。
- `identityToken` 为空时，视为授权失败，不调用 Nalo 登录接口。
- 用户取消授权时返回登录页，不修改已有 Session。
- 客户端必须同时读取 Apple 返回的 `identityToken` 和 `authorizationCode`。
- 当前 Nalo 接口只接收 `id_token`，因此 `authorizationCode` 暂不上传、不持久化。
- TODO：服务端支持后，将 `authorizationCode` 作为 `authorization_code` 随社交登录请求上传。
- Apple 首次授权可能返回用户姓名；当前服务端接口未定义姓名参数，客户端暂不自行保存或上传该字段。
- 不在日志、埋点参数或错误信息中记录 `identityToken`、`authorizationCode` 或 Apple 用户隐私信息。

### iOS 配置

- iOS Runner 开启 `Sign in with Apple` Capability。
- Bundle ID 必须与 Apple Developer 中配置的 App ID 一致。
- Apple Developer 后台完成 Sign in with Apple 能力配置。
- 当前需求只覆盖 iOS；Android 不展示 Apple 登录入口，也不接入 Apple 授权。

## 3. Nalo 服务端登录接口

### 3.1 Apple 社交登录

- 请求：`POST /api/v1/app/auth/social/login`
- 鉴权：不携带 App Access Token。
- Content-Type：`application/json`。
- 请求体：

```json
{
  "provider": "apple",
  "id_token": "eyJhbGciOiJSUzI1..."
}
```

- `provider`：固定传 `apple`。
- `id_token`：Apple 返回的 `identityToken`，必填。
- 客户端不得解析或修改 `id_token`，由服务端校验 Apple 签名、issuer、audience、过期时间和 nonce 等安全字段。

### 3.2 返回数据

服务端返回结构与 Shopify 登录成功响应一致，包含 `data.token` 和 `data.user`：

```json
{
  "code": 0,
  "msg": "登录成功",
  "data": {
    "token": {
      "access_token": "kajahha...",
      "refresh_token": "akjhzha...",
      "expires_in": 900,
      "expires_at": 1786087969
    },
    "user": {
      "id": 1,
      "is_profile_completed": 1
    }
  }
}
```

- `token.access_token`：App Access Token。
- `token.refresh_token`：App Refresh Token。
- `token.expires_in`：剩余有效秒数。
- `token.expires_at`：Unix 秒级过期时间戳。
- `user`：结构与现有 Shopify `exchange.data.user` 一致，用于资料、Welcome 和首页分流。
- 客户端必须同时保存 Access Token、Refresh Token 和过期时间；任一字段无效或保存失败，不得视为登录成功。

## 5. Session、分流与埋点

- Apple 登录成功后复用现有 `authSessionProvider` 更新登录态。
- Token 持久化复用现有 `AuthTokenDto`、`TokenStorage` 和 Auth Repository。
- 登录成功后复用现有用户资料快照和登录后分流逻辑。
- Apple 登录失败、取消、Token 缺失和服务端错误均恢复按钮状态，并在登录页展示错误信息。
- 登录成功后使用统一登录结果埋点，`login_method` 增加 `apple`。
- 登录点击埋点的登录方式增加 `apple`。
- 埋点不得携带 Apple `identityToken`、授权码、邮箱或姓名。

## 6. 依赖影响

- 使用 Flutter 第三方依赖 `sign_in_with_apple` 接入 iOS 原生 Apple 登录。
- 该依赖负责原生授权并能读取 `identityToken` 和 `authorizationCode`；登录页当前使用无按压变色效果的自定义按钮。
- 不修改现有 Shopify OAuth 依赖，不改变 Shopify 登录协议。

## 7. 安全要求

- Apple `identityToken` 只用于本次请求，不写入本地持久化存储。
- 不在普通日志、异常文本、埋点属性中输出 Token。
- 服务端负责 Apple Token 的完整校验，客户端不以 JWT 解码结果作为可信身份依据。
- 使用 nonce 防止重放攻击；如果所选 Flutter 方案支持 nonce，应由客户端生成并传递给 Apple 授权流程，服务端按协议校验。
- Apple 首次授权返回的姓名和邮箱属于隐私数据，除非服务端协议明确要求，不额外保存或上传。

## 9. 完成标准

- 登录页展示 Apple 登录入口，使用通用 Apple 图标和 `Continue with Apple` 文案。
- iOS 首帧直接使用已缓存状态，无缓存时默认显示；有效服务端 `0/1` 响应立即改变显示并永久缓存。
- 无缓存且首次请求失败时，仅在设备报告离线到在线后补试；已有缓存不因网络变化补试。
- 配置请求失败或字段无效时保留缓存/默认显示状态；Android 永远不展示。
- Apple 授权成功后可以取得 `identityToken` 和 `authorizationCode`，且不输出到日志或埋点。
- 客户端向 `/api/v1/app/auth/social/login` 发送 `provider=apple` 和 `id_token`。
- 服务端 Token 返回能复用现有 Token 解析、存储和刷新机制。
- Apple 登录取消、失败、Token 缺失和重复点击都有明确处理。
- 登录成功后能完成现有 Session 更新及登录后页面分流。
- Shopify 登录流程保持不变。
- iOS 已配置 Sign in with Apple Capability。
