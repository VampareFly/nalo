# Shopify 登录注册流程重建需求

## 基本信息

- 日期：2026-08-13
- 服务端协议补充日期：2026-08-17
- 当前状态：开发中；prepare → AppAuth → exchange、Token 临界刷新、登录失效错误码、按用户隔离的 Welcome 本地状态、user/info 和 user/update 已接入；exchange 和 user/update 均直接返回用户信息
- 设计来源：[Nalo v1.2 Figma](https://www.figma.com/design/RXZsVLSYDkFqaHZtHzLX1G/Nalo-v1.2?node-id=0-1&p=f&t=2J70ClQcM0PikG0n-0)
- 实现基准：只以本次选中的 Figma 登录注册流程为准，舍弃项目当前登录注册 UI 和交互
- 架构：Flutter + Riverpod + MVVM，调用方向为 View → ViewModel → Repository → Service → Nalo 服务端 → Shopify

## 目标

删除当前邮箱密码登录、旧注册表单和旧引导分支，按照 Figma 顺序重新实现 Shopify 登录注册流程。

正式流程中，Shopify 授权、Token 交换、身份校验和用户查询由 Nalo 服务端负责。Flutter 不保存 Shopify Secret，也不复刻 Shopify 实际授权页面样式。

过渡阶段保留现有客户端直连 Shopify 登录，并在新入口页提供测试按钮用于授权验证。该入口不是正式业务流程，服务端方案稳定后删除。

## 流程顺序

```text
登录/注册入口页
  ├─ Continue with Shopify ─→ 服务端发起 Shopify 授权
  ├─ Already have an account? Sign in ─→ 服务端发起 Shopify 授权
  └─ I need a kit ─→ 服务端发起 Shopify 授权 ─→ 认证成功后进入 Shop Tab

Shopify 授权回调
  ├─ 已有用户 ─→ 恢复 App Session ─→ 欢迎页或首页
  └─ 新用户 ─→ 资料补充页
                   ├─ 未满 18 岁 ─→ 阻断弹窗
                   ├─ 超过 65 岁 ─→ 风险提示，可 Continue anyway
                   └─ 正常创建账号 ─→ 欢迎页 ─→ 首页
```

Figma 中展示的 Shopify 实际授权弹窗只作为第三方流程示意，不在 Flutter 中实现。

## 1. 登录/注册入口页

### UI

- 蓝色品牌背景。
- Nalo Symbol、Wordmark 和品牌副标题。
- `Login or Sign up` 卡片。
- `Continue with Shopify` 主按钮。
- `I need a kit` 次入口。
- 底部 `Already have an account? Sign in` 入口。

### 交互

- `Continue with Shopify` 和 `Sign in` 都通过 Nalo 服务端发起 Shopify 授权，可分别携带注册或登录意图。
- `Continue with Shopify`、`Sign in` 和 `I need a kit` 发起认证后显示页面级全局 Loading，遮罩并禁止整页交互；成功、失败、取消或异常结束时必须隐藏。

## 2. Shopify 与服务端交互

### 环境

- 测试环境 Base URL：`https://api-test.naloresults.com/`
- 生产环境 Base URL：`https://api.naloresults.com/`
- 两个环境均使用 HTTPS，已删除旧测试域名的 iOS ATS 和 Android cleartext 例外。

### 正式 OAuth 流程

```text
1. 用户点击 Continue with Shopify 或 Sign in
2. App 调用 POST /api/v1/app/auth/shopify/prepare
3. App 把 prepare 返回的 client_id、shop_id、redirect_uri、scope 交给现有 flutter_appauth Shopify 授权能力
4. flutter_appauth 负责打开 Shopify 登录、处理 Deep Link，并完成 PKCE/state 的生成与回调校验
5. App 从授权结果取得 code 和 code_verifier
6. App 携带 code、code_verifier、auth_attempt_id，以及可选 state 调用 POST /api/v1/app/auth/shopify/exchange
7. exchange 返回 Nalo App Token 和 User，至此 Shopify 登录成功
8. App 保存 Token 和当前用户分流快照、更新全局 Session
9. 直接使用 exchange User 完成页面分流，不再追加请求 user/info
```

现有 Shopify 登录能力只复用 AppAuth 授权和 Deep Link 处理，不再由客户端直接向 Shopify Token Endpoint 换 Token。`code_verifier`、`state` 和 `auth_attempt_id` 只在本次授权流程中临时保存，不写日志；授权成功、取消、失败或过期后立即清理。每次点击授权都调用 prepare 创建新的 attempt，禁止复用上一次参数。

### 接口清单

#### 2.1 创建 Shopify OAuth attempt

- 请求：`POST /api/v1/app/auth/shopify/prepare`
- 鉴权：不携带 App Access Token。
- 请求体：当前无业务参数，保留统一 JSON Content-Type 和公共设备 Header。
- 返回字段：
  - `auth_attempt_id: string`，本次登录尝试 ID。
  - `client_id: string`，Shopify OAuth Public Client ID。
  - `shop_id: string`，Shopify 店铺 ID。
  - `redirect_uri: string`，App OAuth 回调地址。
  - `scope: string`，授权范围。
- 客户端收到空字段或非法 URI 时终止授权并显示可重试错误。
- 正式流程的 Dart 代码不写死完整 `redirect_uri`，AppAuth 只使用 prepare 返回值。
- Android `appAuthRedirectScheme` 和 iOS `CFBundleURLSchemes` 仍必须预先注册服务端返回 URI 对应的 Scheme；服务端、原生配置和 Shopify 后台必须保持一致。
- 客户端直连 Shopify 测试入口可以暂时保留固定回调地址，并使用 `// TODO: <pf>` 标记，删除测试入口时一并删除。

#### 2.2 Shopify OAuth code 兑换 App Session

- 请求：`POST /api/v1/app/auth/shopify/exchange`
- 鉴权：不携带 App Access Token。
- JSON Body：
  - `code: string`，Shopify 回调授权码，必填。
  - `code_verifier: string`，本次 PKCE verifier，必填。
  - `auth_attempt_id: string`，prepare 返回的 attempt ID，必填。
  - `state: string`，可选；AppAuth 已在客户端内部校验 state，只有授权结果可以取得且服务端需要时才传递。
- 返回 `data.token`：
  - `access_token: string`。
  - `refresh_token: string`。
  - `expires_in: int`，剩余有效秒数。
  - `expires_at: int`，Unix 秒级过期时间戳。
- 返回 `data.user`：包含 `id`、`email`、`full_name`、`birth_day`、`gender` 和 `is_profile_completed`。
- 客户端优先使用 `expires_at`，并校验其与 `expires_in` 计算结果是否基本一致；字段异常时不得建立 Session。
- exchange 登录成功后，本地必须同时保存 `access_token`、`refresh_token` 和 `expires_at`；任一字段保存失败都不能视为已建立可恢复的 Session。
- 同一 Deep Link 或 attempt 重复兑换时只允许处理一次；服务端需要保证接口幂等。

#### 2.3 刷新 App Token

- 请求：`POST /api/v1/app/auth/refresh`
- 鉴权：不携带已过期 Access Token。
- Body：`refresh_token: string`。
- 返回字段：`access_token`、`refresh_token`、`expires_in`、`expires_at`。
- App 冷启动恢复 Session 时，读取本地 `access_token`、`refresh_token` 和 `expires_at`。
- Access Token 距离 `expires_at` 剩余时间大于或等于 1 天时，直接恢复当前 Session，不调用刷新接口。
- Access Token 尚未过期且距离到期时间小于 1 天时，使用本地 `refresh_token` 调用刷新接口；当前 Access Token 有效期示例为 900 秒，因此每次冷启动通常都会满足刷新条件。
- Access Token 已过期时禁止自动调用刷新接口，立即清理本地 Session，并统一弹出登录失效弹窗。
- 刷新成功后原子替换 `access_token`、`refresh_token` 和过期时间；必须保存服务端返回的新 Refresh Token，不能继续使用旧值。
- 刷新发生网络、超时或系统错误时，如果旧 Access Token 仍未到期，保留旧 Token 并恢复当前 Session。
- 刷新接口返回 `1000002` 或 `1000016` 时，清理本地 Session并弹出登录失效弹窗。
- 多个请求同时发现 Token 过期时，只允许发起一次刷新，其余请求等待同一个刷新结果。

#### 2.4 退出登录

- 请求：`POST /api/v1/app/auth/logout`
- 鉴权：`Authorization: Bearer <access_token>`。
- 成功响应：`code = 0`、`data = null`。
- 无论服务端退出成功、Token 已失效或网络失败，用户明确点击退出后都应清除本地 Token 和当前 User 快照；保留按 userId 绑定的 Welcome 状态。

#### 2.5 获取用户信息

- 请求：`GET /api/v1/app/user/info`
- 鉴权：`Authorization: Bearer <access_token>`。
- 返回 `data.id` 及用户基本信息。
- 该接口保留给后续主动获取服务端最新用户信息；冷启动和 OAuth 成功分流均不调用。
- 完整用户字段尚未提供，客户端 Model 不得根据示例自行猜测字段。

#### 2.6 更新个人信息

- 请求：`POST /api/v1/app/user/update`
- 鉴权：`Authorization: Bearer <access_token>`。
- Body：
  - `full_name: string`，姓名。
  - `birth_day: string`，格式固定为 `yyyy-MM-dd`。
  - `gender: int`：`0` 未知、`1` 男、`2` 女。
- 注册资料页必须选择性别，因此正常提交映射为 Male → `1`、Female → `2`，不主动提交 `0`。
- 更新成功后使用响应 User 覆盖本地分流快照，不再追加请求 user/info。
- 请求期间禁止重复提交；失败时保留表单内容，成功后重新获取或使用服务端返回的最新用户信息进行分流。

### 通用响应与安全约束

- 所有接口统一使用响应包 `{code, msg, data}`，`code = 0` 表示业务成功。
- HTTP 非 2xx、业务非零 code、响应缺字段和 JSON 类型不匹配必须分别映射，不在 Widget 中解析或判断。
- `Authorization`、`code`、`code_verifier`、`state`、`auth_attempt_id`、Access Token 和 Refresh Token 均不得写入日志或 Toast。
- exchange 使用 POST JSON Body，客户端日志仍必须对 code、code_verifier、state 和 auth_attempt_id 脱敏。
- OAuth callback、刷新 Token 和更新资料必须设置超时；自动重试只允许用于明确幂等的请求。
- Access Token 仅访问 Nalo API；客户端不得把 Nalo Token 发送给 Shopify，也不得保存 Shopify Token。

### 业务错误码与客户端处理

#### 登录失效类

以下错误统一清理本地 Access Token、Refresh Token 和内存 Session，只展示一次不可叠加的登录失效弹窗；用户确认后无动画进入登录注册入口：

| code | 含义 |
| --- | --- |
| `1000001` | Access Token 已过期 |
| `1000002` | Refresh Token 已过期 |
| `1000010` | 未授权访问 |
| `1000011` | 登录状态无效 |
| `1000013` | 账号不存在或已注销 |
| `1000016` | Refresh Token 无效或已被吊销 |

- 收到 `1000001` 后不再调用 Refresh Token。
- Refresh 接口返回 `1000002` 或 `1000016` 时立即结束自动刷新流程。
- 登录失效弹窗文案优先使用服务端 `msg`；为空时使用统一英文兜底文案。
- 如果当前本来就没有 Session，则直接停留或进入登录注册入口，不重复弹窗。

#### 认证与用户业务错误

| code | 含义 | 客户端处理 |
| --- | --- | --- |
| `1000012` | 邮箱或密码错误 | 保留输入并展示 `msg`；当前 Shopify 流程通常不会触发 |
| `1000014` | 缺少 `X-Device-ID` | 阻断当前请求，展示通用错误并记录脱敏日志，不清 Session |
| `1000015` | `X-Platform` 不合法 | 阻断当前请求，展示通用错误并记录脱敏日志，不清 Session |
| `1000017` | 邮箱已注册 | 展示 `msg`；不得继续创建重复账号，可引导重新登录 |
| `1000018` | 登录方式未开放 | 停留入口页并展示 `msg` |
| `1000020` | 验证码错误 | 保留表单并展示 `msg` |
| `1000021` | 验证码已过期 | 保留表单并提示重新获取 |
| `1000022` | 验证码场景不匹配 | 停止提交并展示 `msg` |
| `1000023` | 验证码发送过于频繁 | 禁止短时间重复提交并展示 `msg` |

#### 参数与系统错误

| code | 含义 | 客户端处理 |
| --- | --- | --- |
| `4000001` | 未知错误 | 展示通用可重试提示，不清 Session |
| `4000002` | 参数错误 | 展示服务端 `msg`，保留当前表单 |
| `4000003` | 请求过于频繁 | 禁止立即重复提交并展示 `msg` |
| `4000004` | 密码格式不正确 | 保留输入并展示 `msg`；当前 Shopify 流程通常不会触发 |
| `4000005` | 邮箱格式不正确 | 保留输入并展示 `msg` |
| `5000001` | 系统内部错误 | 展示统一可重试提示，不清 Session |

尚未列出的业务 code 按未知业务错误处理：展示 `msg`、保留当前页面和数据、不清理 Session，并通过脱敏日志记录 code。

### 客户端职责

1. 请求 Nalo 服务端创建授权 attempt。
2. 将服务端配置传入现有 AppAuth Shopify 授权能力。
3. 由 AppAuth 生成 PKCE/state、打开 Shopify 页面并处理 Deep Link。
4. 从 AppAuth 授权结果取得 code 和 code_verifier。
5. 携带 code、verifier、attempt ID，以及可选 state 请求服务端 exchange。
6. 保存 Nalo 服务端签发的 App Token，不保存 Shopify Token。
7. 获取用户信息并完成认证后页面分流。

### 服务端职责

1. 创建一次性授权 attempt，并在 callback 时校验 attempt 是否存在、未过期、未使用且属于本次授权配置。
2. 与 Shopify 交换 Token。
3. 查询并校验 Shopify 用户身份和邮箱。
4. 判断 Nalo 用户是否已存在、资料是否完整。
5. 为 App 签发 Access Token 和 Refresh Token。
6. 保证授权回调和账号创建接口幂等。

### 已确认协议与配置规则

- Shopify authorization endpoint 暂按客户端现有规则拼接：`https://shopify.com/authentication/{shop_id}/oauth/authorize`。`shop_id` 必须来自 `prepare` 响应，不得写死具体店铺 ID。
- OAuth 业务流程使用 `prepare` 返回的 `redirect_uri`；App 仍必须在 iOS URL Types/Associated Domains 和 Android intent-filter 中配置与该 URI 匹配的 scheme/host/path，否则授权后无法回到 App。
- `user/info` 新增 `is_profile_completed` 字段：`0` 表示未完善 Profile，`1` 表示已完善 Profile。认证后和冷启动分流应优先使用该字段，不再由客户端通过姓名、生日和性别推断。
- `POST /api/v1/app/user/update` 同时承担首次填写资料和后续修改个人信息。
- OAuth attempt 过期、无效或字段校验失败时，客户端暂不做专用 code 分支：停留当前页、恢复按钮状态并 Toast 展示服务端 `msg`。

### 待服务端补充确认

- Deep Link 取消授权与错误回调的参数格式。
- `prepare`、exchange 和 `user/update` 的完整成功响应 JSON，以及字段可空规则。
- `user/info` 除 `is_profile_completed` 外的完整字段与可空规则。

## 3. 授权结果分流

### 已有用户

- 服务端返回 App Session 后更新全局认证状态。
- 资料未完成：进入资料补充页。
- 资料完整且当前用户的本地 Welcome 标记为已完成：直接无动画进入首页。
- 资料完整但当前用户的本地 Welcome 标记不存在、读取失败或未完成：进入 Welcome 页。

### 新用户

- 进入资料补充页。
- Shopify Email 由服务端返回并在页面只读展示。
- 如果 Shopify 没有返回有效 Email，禁止创建账号，提供重新授权或返回入口页的操作。
- 用户资料提交成功后，无条件进入 Welcome 页面，不受本地历史标记影响。

## 4. 注册资料页

页面元素按 Figma 顺序排列：

1. 返回按钮。
2. Nalo Wordmark。
3. `Create your account.` 标题。
4. Email。
5. Name。
6. Date of birth。
7. Biological sex。
8. `Create account` / `Continue anyway` 按钮。
9. Privacy Policy 和 Terms 说明。
10. 个人信息用途说明。

### Email

- 来自 Shopify 授权结果，只读。
- 客户端提交的 Email 不能作为可信身份，服务端必须根据授权会话确认。

### Name

- 单个输入框，不再拆分 First Name 和 Last Name。
- 去除首尾空格后不能为空。
- 最大长度待服务端确认，建议不超过 100 个字符。
- 键盘 Done 和点击空白区域仅关闭键盘，不触发表单校验。

### Date of birth

- 点击打开英文日期选择器。
- 不允许选择未来日期。
- 建议范围为当前日期至 120 年前。
- 客户端提交格式统一为 `yyyy-MM-dd`。
- 年龄按完整年月日计算，服务端进行最终校验。

### Biological sex

- 仅包含 `Female` 和 `Male`。
- 单选，默认不选择。
- 选中状态按照 Figma：蓝色背景、白色文字。
- 未选中状态：白色背景、蓝色描边及文字。
- 不保留旧流程中的 `Prefer not to say`。

## 5. 表单校验

- 只在点击 `Create account` 或 `Continue anyway` 时校验。
- 输入、失焦、关闭键盘和选择日期时不自动显示错误。
- Email、Name、Date of birth 和 Biological sex 都是必填项。
- 缺少信息时在页面顶部显示 `Please fill in all fields.`。
- 页面需要滚动到第一个无效字段，用户修正后再次点击按钮重新校验。
- 服务端校验结果优先于客户端校验；服务端返回字段错误时保留所有已填写内容。

## 6. 年龄边界

### 未满 18 岁

- 显示不可绕过的 `Under 18` 弹窗。
- 文案按照 Figma。
- 只能点击 `Go back` 返回资料页。
- 不允许创建账号。
- 关闭后保留已填写内容。
- 点击遮罩不能关闭弹窗。

### 18 至 65 岁

- 正常显示 `Create account` 并提交。

### 超过 65 岁

- “超过 65 岁”定义为实际年龄大于 65；刚好 65 岁走正常流程。
- 显示 Figma 黄色健康风险提示。
- 主按钮变为 `Continue anyway`。
- 黄色提示已经承担风险告知；用户点击一次 `Continue anyway` 即提交创建账号请求。
- 修改生日后重新计算；年龄回到 65 岁及以下时移除提示并恢复按钮。

## 7. 创建账号

客户端向 Nalo 服务端提交：

- `full_name`。
- `birth_day`，格式为 `yyyy-MM-dd`。
- `gender`，Male 为 `1`、Female 为 `2`。

当前协议没有独立“创建账号”接口，也没有高龄确认字段。现阶段按 OAuth callback 建立用户身份，再通过 `/api/v1/app/user/update` 补齐资料理解；是否需要提交授权 attempt 或高龄确认状态，需服务端进一步确认。

提交要求：

- 请求期间显示 Loading，禁止重复点击。
- 成功前不能进入欢迎页或首页。
- 网络错误时保留完整表单。
- 请求可以安全重试，不能重复创建账号。
- 授权过期时返回入口页并要求重新授权。
- Email 已绑定账号时转为已有用户登录流程。
- 服务端发现账号已创建时直接恢复该账号 Session。

## 8. 注册成功欢迎页

### UI

- 蓝色品牌背景。
- 个性化欢迎文案，例如 `Welcome, Diana.`。
- `High or low, either way, you know.`。
- 开启通知提醒卡片。
- `Start your Nalo journey` 按钮。

### 交互

- 欢迎称呼优先使用 Full name 的第一个有效单词；无有效姓名时显示 `Welcome.`。
- `Enable notifications` 调用已有通知权限模块。
- 允许或拒绝通知都不能阻塞主流程。
- 点击 `Start your Nalo journey` 后，先为当前用户写入本地 Welcome 已完成标记；保存成功后无动画替换路由进入首页。
- Welcome 标记按服务端 `user.id` 隔离，建议 Key 为 `onboarding_welcome_completed_<userId>`，禁止所有账号共用一个布尔值。
- 本地标记不存在、读取异常或 App 重装后，统一按“未完成”处理并再次展示 Welcome 页。
- 主动退出登录时保留该用户的 Welcome 标记；再次登录同一账号且资料完整时可直接进入首页。
- 写入 Welcome 标记失败时保留在 Welcome 页并允许重试，不能先进入首页再异步保存。
- 首页返回操作不能回到授权、注册或欢迎页。

### 通知权限规则

- 首次安装启动时检查通知权限；尚未授权时自动请求一次系统通知权限。
- 首次请求完成后记录本地标记，非首次启动只检查权限，不再自动弹窗。
- 权限检查、请求或平台调用失败不能阻塞认证和启动流程。
- 欢迎页仅在当前没有通知权限时展示 `Turn on reminders` 卡片。
- 点击 `Enable notifications` 直接打开系统 App 设置页，而不是再次弹出系统请求框。
- App 从设置页回到前台时重新检查权限；已开启后自动隐藏提醒卡片。
- 用户拒绝或未开启通知仍可点击主按钮进入首页。

## 9. 启动和会话分流

```text
无有效 App Session
→ 登录/注册入口页

有 Session，但资料未完成
→ 注册资料页

有 Session，资料完成，但欢迎流程未完成
→ 欢迎页

Session、资料和欢迎流程均完成
→ 首页
```

- 不再使用“是否首次安装”作为登录状态判断。
- App 冷启动时以本地 `expires_at` 为准：剩余时间 `>= 1 天`直接恢复 Session；尚未过期且剩余时间 `< 1 天`时刷新 Token；已经过期时不刷新。
- Session 恢复后读取本地 User 快照的 `isProfileCompleted`、`userId` 和 Welcome 状态直接分流，冷启动不调用且不等待 user/info。
- Access Token 本地已过期或服务端返回登录失效错误码时，清理 Session，显示一次登录失效弹窗，用户确认后无动画进入登录注册入口页。
- 退出登录或 Session 失效时清除当前 User 快照，但保留按 userId 绑定的 Welcome 状态；账号注销清理规则待注销功能接入时补充。
- 登录失效弹窗全局只能同时展示一个；并发请求返回相同错误时不得重复弹窗或重复导航。
- 切换账号、退出登录、应用重装和服务端 Session 失效必须独立处理。

## 10. 异常与边界 Case

- 用户取消 Shopify 授权。
- 授权页面打开失败。
- App Link 重复回调或回调参数缺失。
- OAuth state 不匹配或授权会话过期。
- Deep Link 中存在 OAuth `error`、用户拒绝授权，或缺少 `code`。
- prepare 成功但 App 在打开 Shopify 前被杀死；旧 attempt 不得跨新流程复用。
- exchange 请求超时但服务端可能已完成换 Token；重试必须复用同一 attempt 并依赖服务端幂等。
- `expires_at` 已过期、单位错误，或与 `expires_in` 明显冲突。
- Access Token 刷新期间并发请求导致重复刷新和 Refresh Token 轮换覆盖。
- 服务端返回 HTTP 成功但业务 `code != 0`，或返回体使用 `msg`/`message` 不一致。
- 授权完成但服务端结果仍处理中。
- Shopify 无 Email 或 Email 无效。
- Email 已绑定其他身份。
- 用户重复点击授权、创建账号或 Continue anyway。
- 创建账号请求超时后实际已成功。
- App 在授权过程中被杀死，重新打开后需要恢复或安全重新开始。
- Name 只有空格、超长或包含多语言字符。
- 生日为今天、18 岁临界日、65 岁临界日、闰年生日或未来日期。
- 服务端和客户端计算年龄结果不一致时，以服务端为准。
- 通知权限被永久拒绝时仍可继续进入首页。
- Session 过期时统一回到新入口页，不得回到已删除的旧 LoginPage。

## 12. 依赖影响

- 当前 `flutter_appauth` 用于客户端直接处理 Shopify OAuth；新方案是否继续使用，取决于服务端返回授权地址和 App Link 回调方案。
- 在服务端协议确认前不修改 `pubspec.yaml`，不新增或删除依赖。
- 如果新流程只需要打开网页和接收 App Link，可优先复用项目已有 `url_launcher` 和 `app_links`。
- Token 必须使用项目现有安全存储能力，不得改存 SharedPreferences。
- 测试和生产域名均使用 HTTPS，原生工程不开放明文 HTTP 流量。

## 13. 实施顺序

1. 按已确认的 Shopify 授权端点拼接和 Deep Link 配置规则完成联调，错误暂统一展示服务端 `msg`。
2. 新建服务端认证 Model、Service 和 Repository 接口。
3. 实现登录/注册入口页及授权回调状态机。
4. 实现资料页、表单校验和年龄边界。
5. 实现注册成功欢迎页和通知入口。
6. 更新启动分流、Session 过期处理和无动画首页跳转。
7. 删除旧登录注册页面和 ViewModel；客户端直连 Shopify 代码待服务端流程稳定后删除。
8. 清理无引用组件、路由、埋点和依赖。
9. 更新 `nalo.md` 及相关代码注释。

## 14. 完成标准

- 项目中不再存在旧邮箱密码登录注册入口。
- App 不直接请求 Shopify Token Endpoint。
- Figma 选中的入口、资料、错误、年龄提示和欢迎状态均有对应实现。
- 未满 18 岁无法创建账号；超过 65 岁显示黄色风险提示，点击一次 `Continue anyway` 即可提交。
- 已有用户、新用户、资料未完成用户和欢迎未完成用户分流正确。
- 用户资料完成状态以服务端 `is_profile_completed` 为准，`0` 进入资料页，`1` 继续 Welcome/首页分流。
- 授权取消、网络失败、重复回调和重复提交都有明确处理。
- 登录或注册完成后无动画进入首页，返回键不会回到认证流程。
- Session 过期统一返回新入口页。
- 冷启动 Token 临界值严格遵循 `>= 1 天`恢复、未过期且 `< 1 天`刷新、已过期不刷新。
- 资料提交成功必然进入 Welcome；Welcome 本地状态按用户 ID 隔离并在冷启动分流中生效。
- 新增核心文件和公开 API 都包含符合项目规范的中文注释。
